Le projet

STAS est un runtime contemporain conçu pour exécuter des programmes écrits en STOS BASIC, le dialecte BASIC de l'Atari ST popularisé à partir de 1988 par STOS Software et François Lionet. L'objectif est double : rejouer les programmes historiques avec la plus grande fidélité possible, et permettre d'écrire de nouvelles démos ou de nouveaux jeux dans une syntaxe et des abstractions proches de l'original.

Le runtime s'articule autour d'un cœur d'interprétation écrit en JavaScript pur, sans dépendance externe. Il tokenise un programme, simule sa machine virtuelle (variables, tableaux, instructions graphiques et sonores) et produit une sortie adaptable au navigateur ou au terminal.

À la différence d'un émulateur Atari complet, STAS ne reproduit pas le système d'exploitation ni le matériel : il réimplante la sémantique du langage et des primitives graphiques, ce qui le rend léger et directement exploitable dans un navigateur moderne ou sous Node.js.

Pourquoi STAS ?

STOS BASIC était livré avec l'Atari ST et utilisait directement les traps VDI du système pour afficher texte, graphismes, sprites et fenêtres. Recréer ce dialecte sans Atari ni GEM implique de fournir un nouvel environnement d'affichage et d'entrées/sorties. STAS choisit de remplacer ces traps matérielles par un buffer unique de cellules de caractères, facilement affichable soit en terminal ANSI, soit en canvas HTML.

Cette approche offre plusieurs avantages. Elle rend le moteur indépendant de la plateforme : le même programme tourne dans le terminal et dans le navigateur sans modification. Elle permet de jouer avec des résolutions variables et des modes de rendu variés. Elle conserve l'esprit original : programmer en STOS, c'était avant tout manipuler un écran de caractères et quelques primitives graphiques simples.

Démarrage rapide

Après le clone, l'installateur vérifie Node.js (≥ 18, aborte proprement sinon), installe la commande stas (PATH sous Windows, wrapper sous macOS/Linux) et valide par la suite de tests : 

# Windows (PowerShell, cmd ou double-clic)
install.bat

# macOS / Linux
./install.sh

Aucune installation npm n'est nécessaire. Le projet utilise les modules ES natifs de Node.js et des imports relatifs. Sans l'installateur, les commandes restent accessibles directement : 

# Console interactive (invite "Ok", fidèle au STOS)
node STAS/packages/stas-console/bin/stas.js

# Exécuter un programme
node STAS/packages/stas-console/bin/stas.js STAS/examples/sinus.bas

# Version web (serveur local)
node STAS/packages/stas-web/serve.js

La version web est accessible à l'adresse http://localhost:8080/packages/stas-web/index.html. La racine du serveur est le dossier STAS/, ce qui permet aux chemins relatifs et à l'importmap de fonctionner sans bundler.

Astuce : depuis la racine STAS/, le script npm run serve lance également le serveur.

Architecture

Le STOS original empilait ses traps maison (FENETRE.S, SPRITES.S, FLOAT.S, MUSIC.S) au-dessus des traps système GEMDOS, VDI, BIOS et XBIOS. STAS remplace toute cette pile par un interpréteur JavaScript et un buffer de cellules.

source.bas → tokenizer → stas-core → ascii-buffer (cellules ch/fg/bg) → stas-web ou stas-console → renderer

stas-core

Cœur du runtime : tokenisation, évaluation des expressions, boucles, gestion des écrans physic et logic 320 × 200, convertisseur ASCII, gestion des sprites et de la palette STOS 16 couleurs.

stas-web

Adaptateur navigateur. Il relie l'interpréteur au DOM via un élément <canvas>, gère le clavier et expose une API postMessage pour l'intégration dans des iframes ou des applications hôtes.

stas-console

Adaptateur Node.js. Il affiche la sortie graphique sous forme d'art ASCII en utilisant des couleurs ANSI 24 bits et les caractères de blocs quadrants, permettant l'animation directement dans un terminal.

stas-world

Pont AWI-HAXE / AOZ Studio. Il ajoute une couche de navigation entre mondes, de shell hôte et le protocole WorldSTAS pour orchestrer plusieurs instances.

Comparaison avec le STOS original

STOS (1988)STAS

La langue V1

STAS V1 implante un sous-ensemble fidèle du langage STOS BASIC. Les tokens sont reconnus de manière insensible à la casse, mais listés en minuscules. Les variables restent sensibles à la casse, les noms sont complets et le suffixe $ désigne une chaîne.

Structures et flux

GOTO, GOSUB/RETURN/POP, FOR/TO/STEP/NEXT, WHILE/WEND, REPEAT/UNTIL, IF/THEN/ELSE (forme une-ligne), ON n GOTO|GOSUB, DIM, DATA/READ/RESTORE [n], REM / ', et : pour enchaîner les instructions.

Affichage

PRINT / ? (le point-virgule supprime le saut de ligne, la virgule crée des taquets de 14 colonnes, TAB(n) positionne), CLS, LOCATE x,y (0-based), PEN n, PAPER n, HOME, CUP/CDOWN/CLEFT/CRIGHT, INC/DEC.

Entrées

INPUT ["texte";] v[,v2...], LINE INPUT, INKEY$ (non bloquant).

Mathématiques et chaînes

ABS INT SQR SGN SIN COS TAN ATN EXP LN LOG PI MIN MAX RND DEG RAD — LOG est en base 10 comme dans le STOS, et DEG/RAD changent le mode des trigonométriques.

Chaînes : CHR$ ASC LEN LEFT$ RIGHT$ MID$ STR$ VAL SPACE$ STRING$ INSTR UPPER$ LOWER$ HEX$ BIN$, plus TIMER (compteur 50 Hz), TRUE/FALSE.

Commandes directes

RUN [n], LIST [n|n,m|n-m|n-|-m], NEW, SAVE ["fichier"], SAVE AS ["fichier"], LOAD ["fichier"], DEL/DELETE, CLEAR, WAIT n (n × 20 ms), END, STOP, ERROR n, ENGLISH/FRANCAIS.

SAVE / LOAD transitent par un connecteur (stas:save, stas:load) au format des messages AWI — réponse Answer { success, error, data, message } comme EdHttp. La console branche un mockup local (fichiers sur disque) ; plus tard, le ConnectorStas d'AWI prendra la main (comptes, sécurité, stockage Volt.A). Sans nom de fichier, SAVE réutilise le fichier courant — SAVE AS en demande un nouveau. Le préfixe examples: désigne le dossier examples/ de l'installation, quel que soit le répertoire courant : LOAD "examples:hello.bas".

Limites V1 : IF ... THEN ... ELSE reste sur une seule ligne. Pas de DEF FN, pas de ON ERROR GOTO. Le dessin connait INK, RBOX/RBAR, CENTRE, DRAW x,y TO x,y, RESERVE AS SCREEN + START(n), l'affectation LOGIC=/PHYSIC=, et les réglages écran FLASH/KEY/CLICK/HIDE (sans effet) ; PLAY est accepté mais silencieux. Le reste du vocabulaire STOS (sprites, musique, fenêtres, banques de données) est tokenisé fidèlement mais renvoie l'erreur 20 « Function not implemented » — la table des tokens est complète et le terrain est prêt pour les prochaines itérations.

Les renderers

Un même programme STAS peut être affiché de plusieurs manières. Le choix du renderer se fait par le paramètre d'URL renderer ou dans la section [web] d'un fichier INI.

défaut

CanvasRenderer

Le renderer historique. Chaque cellule de la grille texte est rendue comme un bloc de couleur ou un glyphe. Équilibré entre lisibilité du texte et aspect graphique. C'est le mode par défaut si aucun renderer n'est précisé.

ascii-art

AalibRenderer

Convertit le plan graphique 320 × 200 en art ASCII à l'aide d'une palette de caractères. Donne un rendu rétro-terminal très marqué. Nécessite le fichier vendor/aalib.js.

natif

PixelRenderer (alias atari)

Copie le buffer graphique 320 × 200 pixel par pixel dans un canvas, avec une mise à l'échelle sans lissage. Reproduit l'aspect le plus proche de l'affichage original sur Atari ST.

terminal

Console ANSI

Utilisé par l'adaptateur Node.js. Le buffer graphique est converti en caractères de blocs et en couleurs ANSI 24 bits, permettant une animation en ascii-art dans un terminal moderne.

Transparence et faux-noir

Pour résoudre les problèmes de transparence, en particulier dans le renderer AALib, STAS peut utiliser une couleur transparente. L'éditeur de sprites du STOS original proposait une option similaire lors de l'importation d'images.

Le principe est simple : on choisit une couleur, par exemple le noir pur (0,0,0), comme couleur transparente. Le noir réel devient alors (0,0,1), imperceptible à l'œil humain mais distinct pour le moteur. Ainsi, même les images avec palette conservent leurs couleurs originales (sauf le noir qui devient 0,0,1) et disposent en plus d'une couleur transparente.

En résumé : le noir (0,0,0) joue le rôle de couleur transparente, tandis que le noir affichable est cartographié vers (0,0,1). Cela aide le renderer ASCII-art à distinguer fond et sprite.

Résolutions texte et graphique

STAS distingue deux résolutions qui peuvent être identiques ou découplées : la résolution du buffer texte et la résolution du renderer graphique.

  • Buffer texte : la grille de caractères sur laquelle les commandes PRINT, LOCATE, CLS opèrent.
  • Renderer graphique : la grille utilisée pour convertir l'image 320 × 200 en caractères ou en pixels affichables.

Paramètres disponibles

ParamètreExempleSignification
res=WxH res=160x50 Applique la même résolution au buffer texte et au renderer.
text=WxH text=80x25 Verrouille la grille du buffer texte. MODE ne la redimensionne plus.
gfx=WxH gfx=160x50 Définit la grille de conversion du renderer AALib, indépendamment du texte.

Les valeurs doivent être des diviseurs de 320 × 200 pour éviter les blocs fractionnaires. Les combinaisons courantes sont 80x25, 160x50, 320x200. Sans indication, la fidélité STOS est totale : la commande MODE du programme choisit la grille.

Compatibilité : le paramètre gfx= n'a de sens que pour le renderer aalib, qui sait découpler la grille graphique de la grille texte. Les renderers canvas et pixel suivent la résolution texte ou la résolution native 320 × 200. Si une combinaison invalide est demandée, un avertissement est émis dans la console du navigateur et le paramètre est ignoré.

Sortie console

La sortie console ne peut pas afficher de graphique bitmap, mais elle travaille en ascii-art. Le buffer graphique 320 × 200 est converti en caractères de blocs quadrants et colorisé avec des séquences ANSI 24 bits.

Cette approche permet de gérer des animations dans un terminal moderne. La démo du sinus animé, par exemple, fonctionne parfaitement en console : chaque frame est rasterisée en caractères et affichée à la cadence du programme.

Comportement au redimensionnement du terminal

Par défaut, la zone de render console n'est pas retaillée automatiquement lorsque la fenêtre du terminal change de taille. Ce comportement peut être rendu optionnel via un paramètre de configuration, afin de préserver la cohérence visuelle des programmes qui supposent une taille d'écran fixe.

Exemple

node packages/stas-console/bin/stas.js examples/sinus-anim.bas

Fonctionnement dans le navigateur

Le serveur de développement inclus dans le package stas-web sert l'ensemble du dossier STAS/ comme racine et redirige / vers /packages/stas-web/. Les chemins ne reprennent donc pas le segment /STAS/ dans l'URL. 

# Depuis la racine STOS/
npm run serve
# ou directement
node STAS/packages/stas-web/serve.js

Le serveur écoute par défaut sur http://localhost:8080.

Configuration INI

Comme le nombre d'options augmente, un fichier INI simple permet de centraliser les réglages. La section [web] accepte les clés renderer, res, text, gfx et run. 

; stas.ini
[web]
renderer=pixel
res=80x25
run=examples/sinus-anim.bas

Chargement depuis l'URL :

http://localhost:8080/packages/stas-web/index.html?config=stas.ini
Priorité : les paramètres passés dans l'URL écrasent ceux du fichier INI. Cela permet de surcharger rapidement un réglage sans modifier le fichier de configuration.

Intégration dans une iframe

L'application web peut être embarquée dans une balise <iframe> et contrôlée depuis la page parente via une API postMessage. Cela permet d'intégrer STAS dans un site, un éditeur de code, un wiki ou un autre framework.

Messages parent → iframe

Tous les messages entrants doivent contenir target: "stas".

TypeDonnéesEffet
runsource?, id?Charge et exécute le programme.
loadsource?, id?Charge sans exécuter.
playid?(Re)lance ou reprend l'exécution.
pauseid?Suspend l'exécution.
resumeid?Reprend après une pause.
stopid?Interrompt l'exécution courante.
resetid?Stop et réinitialise complètement.
inputtext, id?Envoie une ligne en réponse à une saisie.

Messages iframe → parent

Tous les messages sortants portent source: "stas".

TypeDonnéesSens
ready—Le moteur est prêt.
loadedid?Source chargée.
doneid?Exécution terminée normalement.
stoppedid?Arrêt demandé ou BREAK.
errormessage, codeErreur d'exécution.
input:request—L'engine attend une ligne de saisie.
outputtextContenu texte final du buffer.

Exemple d'intégration

<!-- Page hôte -->
<iframe id="stasFrame"
        src="http://localhost:8080/packages/stas-web/index.html"
        allow="fullscreen"
        sandbox="allow-scripts allow-same-origin">
</iframe>

<script>
  const iframe = document.getElementById('stasFrame');

  function stasCommand(type, payload = {}) {
    iframe.contentWindow.postMessage(
      { target: 'stas', type, ...payload },
      '*'
    );
  }

  window.addEventListener('message', (e) => {
    if (e.data?.source !== 'stas') return;
    console.log('STAS:', e.data.type, e.data);
  });

  // Lancer un programme après quelques secondes
  setTimeout(() => {
    stasCommand('run', { source: '10 PRINT "HELLO"\n20 END' });
  }, 2000);
</script>

Le champ target: 'stas' est obligatoire pour que l'iframe reconnaisse le message. Les messages sortants portent source: 'stas'. Le champ optionnel id permet de corréler les accusés de réception avec les commandes envoyées.

Cas d'usage typiques

  • Éditeur en ligne : un bouton « Run » dans une page envoie le contenu d'un éditeur de texte vers l'iframe via run.
  • Documentation interactive : plusieurs iframes affichent des exemples de programmes STOS sans quitter la page.
  • Intégration AWI-HAXE / AOZ Studio : un composant hôte enveloppe les messages postMessage dans des méthodes play(), pause(), stop(), etc.

À retenir : quelle que soit la cible (navigateur ou terminal), le langage reste le même. Seul le renderer change, et le programme peut être déplacé d'une plateforme à l'autre sans modification.
